# Development Task Checklist Standard

## 目标

把需求整理成开发人员可以逐项执行、产品或业务人员可以逐项确认、发布人员可以据此升级和验收的任务清单。

清单不能只是需求摘要。它必须回答：改什么、为什么改、改到哪些有效入口、数据库如何升级、旧客户如何兼容、配置如何组合、失败时如何回退、完成后如何验收。

## 核心原则

1. **先查项目，再写清单。** 文件存在不等于正在使用；必须核对项目文件收录、主菜单或启动入口、窗体跳转、业务调用方和数据访问链路。
2. **只写真实功能。** 不得因为相邻项目、旧分支或磁盘目录里存在某个窗体、复制、导入、接口、四层代码，就把它写进清单。
3. **保持现有语言和架构。** 现有 VB 继续按 VB 修改，现有 C# 继续按 C# 修改；除非用户明确提出，否则不把需求清单扩展成语言迁移或架构重构。
4. **业务确认与开发状态分开。** 已确认的规则和已核查的范围用 `[x]`；尚未实施的开发项用 `[ ]`。不要把“需求已确认”误写成“代码已完成”。
5. **覆盖完整闭环。** 数据库、配置、录入、保存、完成、撤销、返单、查询、动态占用、流水、公共选择控件、升级注册和发布包含必须一起检查。
6. **兼容规则必须可执行。** 老数据、旧程序、未完成单据、配置启停和默认值都要写出明确行为，不使用“做好兼容”这类空话。
7. **升级脚本是开发任务的一部分。** 只要涉及表、字段、索引、视图、配置或字典，就必须写升级脚本、重复执行保护、升级检测、脚本注册和项目发布包含任务。
8. **用户只决定业务选择。** 参数号冲突、项目收录、调用链、SQL 写法等技术事实由项目检索确认；只有会改变业务结果的选项才交给用户拍板。

## 工作流程

### 1. 读取约束和现有标准

- 完整读取仓库中的 `AGENTS.md`、适用的项目级 skill、既有开发任务和相邻升级脚本规则。
- 若仓库已有 `开发任务` 目录和命名惯例，沿用它；不要再创建 `task_plan.md`、`findings.md` 等同类交付物来替代用户要求的清单。
- 读取与需求直接相关的旧清单，提炼格式，不照抄其中未经核实的文件路径和模块范围。

### 2. 建立项目事实

至少核对以下证据：

- 主解决方案、启动项目和启动入口。
- `*.csproj`、`*.vbproj` 中的 `Compile`、`Content`、`ProjectReference`。
- 主菜单、按钮、反射注册、路由、窗体跳转或服务注册入口。
- 当前业务调用链：列表/单头 → 明细 → 完成/撤销 → 库存或核心事实表。
- 当前查询、公共下拉、选择弹窗、流水和报表的数据来源。
- 同名旧文件、备份目录、注释入口、未被项目收录的代码和无调用自动生成层。
- 明确不适用的帐套、模块、独立子系统和外部项目。

检索时优先使用 `rg`。遇到同名实现时，以项目收录和活动入口为准，不以文件修改时间或目录名称猜测。

### 3. 还原业务规则

从用户对话和现有代码中整理：

- 现行规则和新规则。
- 配置粒度：帐套级、公司级、用户级或全局。
- 多个配置是否独立；若独立，给出所有组合的真值表。
- 字段来源：手工录入、单头带入、字典选择、计算或系统生成。
- 空值、默认值、长度、字符范围、唯一性和大小写规则。
- 配置关闭、启用、历史数据、旧单据和旧程序的处理方式。
- 明确禁止的实现，例如自动编号、复用错误字段、跨模块改造或自动合并历史数据。

如果对话已经给出答案，直接标记已确认，不重复询问。只有不同选择会造成不同业务结果时才请求用户确认，并优先给出推荐方案和影响。

### 4. 核对数据库和旧程序兼容

涉及数据库字段时，清单必须明确：

- SQL 类型、长度、`NULL/NOT NULL`、默认值和空字符串语义。
- 源字段和目标字段类型不同的转换规则，例如 `Trim/RTRIM`。
- 历史记录回填规则以及升级后的校验 SQL。
- 唯一键、普通索引、视图、联接、分组、缓存键和 DataTable 主键的调整。
- 新增和更新参数的 `SqlDbType` 及禁止 `DBNull` 的规则。
- 默认值是否真能兼容旧程序：搜索活动 `INSERT`，确认旧代码显式列出字段；若存在不带字段名的 `INSERT ... VALUES(...)`，必须把它列为升级前阻断项。
- 完成、撤销、返单和异常回滚是否处于正确事务边界。

### 5. 写入任务文件

- 新文件默认命名为 `yyMMdd<简明任务名>开发任务.md`。日期必须取自可信的当前日期来源，不凭模型记忆猜测。
- 用户要求修改已有清单时保留原文件名，除非用户明确要求重命名。
- 优先写入项目已有 `开发任务` 目录；若不存在，沿用仓库现有文档目录。
- 使用 `references/development-task-checklist-template.md` 作为结构基线，根据需求删去不适用章节，不为了形式保留空章节。
- 文件顶部写清状态、适用范围、不适用范围、核心目标、实现边界和勾选说明。

### 6. 做反向审查

完成初稿后，从以下三个方向反查：

1. **误加项**：没有入口、未被项目收录、仅旧目录使用、只在排除模块存在、自动生成但无调用的代码。
2. **漏加项**：升级脚本、升级注册、项目 `Content`、公共控件、选择弹窗、流水、撤销返单、动态占用、历史数据和配置关闭保护。
3. **冲突项**：字段类型不一致、默认值与空值语义冲突、启用规则与旧单兼容冲突、配置组合遗漏、清单说不重构但又列出迁移任务。

使用全文搜索验证关键字段、旧路径、排除类名、数据库类型和状态说明。文档修改不需要编译项目；只有实际代码发生变化时才按对应项目规范编译。

## 清单内容标准

### 顶部元信息

至少包含：

- 状态。
- 适用系统、帐套或模块。
- 明确排除范围。
- 核心目标。
- 实现边界，例如保持现有语言、不改独立仓储模块。
- 勾选语义：确认状态和开发状态如何区分。

### 已确认规则

- 用准确字段名和业务名描述。
- 配置独立时给出组合矩阵。
- 明确写入规则、显示规则、必填规则和唯一性规则。
- 把用户已确认的规则标记为 `[x]`。
- 单列“明确禁止”，防止开发人员自行扩展需求。

### 项目入口核查

- 记录当前有效入口和项目收录证据。
- 记录已排除的旧实现、重复实现和无调用层。
- 区分“数据库对象仍在使用”和“对应自动生成代码没有调用”。
- 对只可能由外部系统使用的对象，写成条件性风险，不把它伪装成当前项目入口。

### 开发任务

按实际项目选择章节，通常包括：

- 系统配置及配置界面。
- 数据库升级脚本、注册、项目包含、表、索引和视图。
- 真实调用链中的 Model/BLL/IDAL/DAL 或现有 VB/DataTable/直接 SQL。
- 主业务录入、保存、完成、撤销和事务。
- 下游业务模块。
- 查询、动态占用、流水、公共控件和弹窗。
- 历史数据、旧程序、未完成单据和配置启停。
- 实施顺序、依赖关系、验收矩阵和风险控制。

所有尚未开发的任务保持 `[ ]`，即使其业务规则已经确认。

### 验收标准

- 验收项要能操作和观察，不能只写“功能正常”。
- 多配置需求按配置组合分别验收。
- 覆盖新增、修改、完成、撤销、返单、查询、合计、流水和升级重跑。
- 覆盖数量、重量、金额等守恒要求。
- 覆盖旧客户默认配置和排除模块不受影响。
- 覆盖数据库空值、默认值、重复键和脚本可重复执行。

## 写作要求

- 先写结论和规则，再写实施细节。
- 使用项目真实路径、字段、类名和配置号；不能确认的技术事实写成开发核查项，不凭空决定。
- 同一术语全文保持一致，例如“采购客户”不要在不同章节随意换成“供应商”而不说明。
- 任务粒度以一个开发人员可以明确判断完成为准，避免一条任务包含十几个无关动作。
- 对 SQL、组合键和配置矩阵使用代码块或表格，减少歧义。
- 不在清单中生成大段实现代码；必要时只给字段定义、键结构或参数类型示例。
- 不写项目不存在的复制、导入、打印、接口或测试功能。
- 用户要求日期前缀时必须落实到文件名；项目已有日期前缀惯例时默认沿用。

## 交付前检查

- [ ] 文件名前有可信日期，路径符合仓库习惯。
- [ ] 第 1～2 节确认项全部与用户最终决定一致。
- [ ] 第 3 节以后未开发任务没有被误勾选。
- [ ] 适用范围和排除范围明确。
- [ ] 已核对项目收录、入口和调用链。
- [ ] 没有把旧文件、注释入口或无调用四层代码列为必改项。
- [ ] 现有 VB/C# 等语言保持不变，除非用户明确要求迁移。
- [ ] 字段类型、长度、默认值、空值和参数类型全文一致。
- [ ] 默认值对旧程序的兼容已经用实际 `INSERT` 写法验证。
- [ ] 升级脚本、升级检测、脚本注册和项目发布包含形成闭环。
- [ ] 主流程、下游模块、公共选择、查询、动态占用和流水都已覆盖。
- [ ] 历史数据、旧程序、未完成单据、配置启用和关闭均有明确规则。
- [ ] 实施顺序有依赖关系，验收按业务组合覆盖。
- [ ] 不存在用户已否认的功能或未经授权的范围扩张。
