# 通用后端 API 规范

本规范只定义可跨项目复用的 API 原则。先读取目标仓库的项目规范和现有实现；项目已确认的契约优先于本规范中的默认建议。

## 一、开始修改前

1. 阅读相关 Endpoint/Controller、请求与响应模型、业务服务、数据访问层和调用方。
2. 确认现有路由、HTTP 方法、响应封装、错误模型、鉴权方式、分页结构和兼容性要求。
3. 优先复用仓库已有的中间件、过滤器、验证器、事务封装、权限入口和文件服务。
4. 保持修改聚焦，不借 API 需求进行无关重构或引入新的架构体系。

## 二、HTTP 契约

- 路由表达资源或明确的业务动作，避免 `Process`、`Handle`、`DoSomething` 等含义模糊的命名。
- HTTP 方法与语义一致：读取使用 GET，创建使用 POST，整体替换使用 PUT，局部修改使用 PATCH，删除使用 DELETE；若项目已有明确约定则沿用项目约定。
- 固定子路径应避免与参数路由冲突；参数路由使用类型或格式约束，例如 ASP.NET Core 的 `{id:long}`。
- 查询参数用于筛选、排序和分页；复杂写入参数使用请求体；文件上传使用明确的 multipart 契约。
- 不随意修改既有字段含义、类型、默认值、枚举编码或错误码。需要破坏性变更时采用版本化或兼容迁移。
- 分页接口返回数据、总数、页码和页大小等完整元数据，并对页大小设置服务端上限。
- 批处理接口限制单批大小，返回稳定的进度、成功/失败计数和可定位到单项的错误信息。

## 三、请求与响应模型

- API 边界使用专门的请求/响应模型，不直接暴露数据库实体或持久化模型。
- 请求模型只包含客户端允许控制的字段，防止 over-posting；创建审计字段、租户字段和权限归属字段由服务端产生。
- 响应模型保持稳定、可序列化且不泄漏内部异常、绝对文件路径、密钥或实现细节。
- 标识符、日期时间、金额和枚举的序列化方式在同一 API 中保持一致。
- 对大结果、错误集合和文件内容使用分页、流式响应或下载文件，避免一次返回无界数据。

## 四、分层职责

- Endpoint/Controller 负责模型绑定、鉴权声明、协议转换和统一响应，不直接拼接复杂查询或执行业务事务。
- Service 负责业务校验、数据权限、状态变化、跨表操作、事务和领域事件。
- 数据访问层负责查询组合、持久化和统一的数据范围过滤；不要在多个 Controller 重复实现权限条件。
- 映射逻辑保持集中，避免请求模型、实体和响应模型之间散落重复转换。
- 避免为机械拆分而编写仅包含一行实现的函数，或仅有一个调用方且不具备独立业务语义、复用价值或测试边界的函数；此类逻辑优先在调用处直接表达。

## 五、校验与错误处理

- 边界校验处理必填、长度、范围、格式和集合大小；业务服务处理唯一性、关联存在性、状态、权限和并发冲突。
- 所有客户端输入均不可信，包括路径参数、隐藏字段、文件名、分页大小和批次令牌。
- 使用统一、可预期的业务错误响应；客户端可修正的问题应返回明确字段和原因。
- 不向客户端返回堆栈、SQL、连接信息或原始内部异常消息；详细异常记录到受控日志。
- 多条校验错误应去重并可定位到具体字段、记录或来源行。

## 六、认证、授权与数据范围

- 认证只证明身份，授权决定动作，数据范围决定可访问记录；三者分别校验。
- 列表、详情、导出、统计、按主键查询和文件下载必须经过一致的数据权限入口。
- 写入前校验操作者对所有来源对象、目标对象和归属范围的权限，不能只验证请求中的一个主键。
- 权限集合为空时默认拒绝，不把空集合解释为全部权限。
- 不信任客户端提交的租户、组织、区域、所有者或角色字段来决定权限。

## 七、事务、并发与幂等

- 跨表写入、状态变更、事件记录和批处理中的原子步骤建立清晰事务边界，并检查事务结果。
- 异常必须触发回滚；不要在事务内吞掉异常后继续提交。
- 对重复提交有风险的创建、支付、导入和批处理接口设计幂等键或稳定状态机。
- 缓存中的可变批次状态必须按批次或令牌串行化；不要并发修改共享 `List`、索引和计数器。
- 并发更新使用数据库约束、乐观并发标记、锁或可证明安全的原子操作，不能只依赖“先查再写”。
- 服务端限制批次大小、分页大小、文件大小、记录数和处理时长，客户端参数不能解除这些上限。

## 八、文件、导入与导出

- 上传同时校验扩展名、内容类型、文件签名、大小、记录数和模板契约；文件名不能直接用于拼接存储路径。
- 下载和导出先校验权限，并使用受控文件标识定位文件；规范化路径后确认仍位于允许目录。
- 敏感导入导出关闭不必要的请求/响应日志，错误文件和临时文件使用私有存储并设置清理策略。
- 大型导入采用可恢复的批次状态和稳定进度；中断重试不能重复处理已完成记录。
- 错误报告应能定位来源记录，但不得因为错误信息而扩大敏感数据暴露。

## 九、日志与安全

- 对重要写入、导入、导出、权限变化和复合事务记录审计日志，同时避免记录密码、令牌、完整证件号等敏感值。
- 密码只保存成熟哈希结果；密钥和连接信息通过受控配置管理，不进入源码或响应。
- 对外部 URL、回调、重定向、文件路径和表达式输入进行白名单或严格解析，防止 SSRF、路径穿越和注入。
- 错误处理、审计和权限过滤不能只存在于前端。

## 十、完成前检查

- 路由和 HTTP 方法是否明确且无冲突。
- 请求字段是否最小化，响应是否稳定且有界。
- Controller 是否保持轻量，业务与事务是否位于 Service。
- 列表、详情、导出、统计和文件入口是否使用同一权限边界。
- 唯一性、关联、状态、并发和幂等是否在服务端处理。
- 事务失败是否整体回滚，批次和缓存状态是否并发安全。
- 日志、错误响应和文件访问是否避免泄漏敏感信息。
- 是否完成与风险相称的构建、静态检查和定向验证。
